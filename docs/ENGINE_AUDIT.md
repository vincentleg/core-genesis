# V0 technical audit — October 17, 2026

The preserved V0 evidence genuinely demonstrates 0/6 → 2/6 with six physical model requests. It does not yet demonstrate deep team evolution.

1. **Roles are context, not execution boundaries.** All actual repairs come from the same Executor batch. Role membership and duties do not dispatch separate specialized workers.
2. **Workflow is only a prefix filter.** Steps before `repair` decide evidence access; steps after it have no operational effect.
3. **Verification evolution is mostly advisory.** `preflight` changes the prompt, but a distinct reviewer does not execute. Final deterministic checks are real and must remain mandatory.
4. **No within-run generations.** Each click tests two siblings once; the next run may restore the winner. A version number is not a generation or a parent-child lineage.
5. **No persistent lessons.** The Observer identifies failures but its lessons and reusable procedures are not carried forward as verified memory.
6. **Tiny, repeatedly reused holdout.** Three held-out fixtures are excluded from mutation prompts, but repeated use permits indirect adaptation. Numeric variations within three families are not evidence of broad software repair.
7. **No objective input or measurable objective contract.** The product runs a fixed demonstration; it does not expose a scoped user goal and its criteria.
8. **Accuracy ceiling.** Tool access improves routing, but the model still misses timeout inequalities, retry constraints and worker preservation. Repeated pointwise inference spends tokens without making these operations reliable.
9. **Incomplete comparisons.** The Arena lacks real parent relationships, mutation diffs, separate round comparisons and fresh validation manifests.
10. **Important strengths to preserve.** Existing Crusoe client, model/usage records, bounded JSON patches, six-request physical quota, two-cycle ceiling, persistent $2 budget, fail-closed pricing, no automatic inference, deterministic final verification and genuine historical evidence.

## V2 implementation direction

Crusoe/Nemotron proposes team configurations and compiles small declarative repair programs. A bounded interpreter executes typed field operations and explicit agent workflows; it never evaluates generated code. Specialized agents have enforced field ownership and tool capabilities. Verification, evidence caching and inherited development-verified rules execute locally and produce traces.

Run generation 0 plus three mutation rounds. Each round has two siblings, a development-only selection, fresh reproducible held-out instances, parent re-evaluation on identical instances, regression checks, and a deterministic promote/rollback decision. A final sealed challenge measures the active team without informing further mutation. Never invent a promotion to complete the graph.

At most eight planned model calls across two cycles: Architect, baseline Executor, then one combined Observer/Scientist call and one Executor compilation call per round. Independent execution/evaluation is local. Retries count toward the unchanged six-physical-request-per-cycle quota; the unchanged $2 project ledger remains authoritative.

This changes the experiment from pointwise prompt repair to **model-synthesized, capability-limited team procedures**. The benchmark remains a scoped configuration-incident simulator. It does not become arbitrary repository repair or unrestricted self-modification.
